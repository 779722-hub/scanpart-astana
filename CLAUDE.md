Я даю тебе набор правил для кодинга под названием Karpathy Skills

Это CLAUDE.md с четырьмя принципами:

Think Before Coding (думай перед тем, как писать код)
Simplicity First (простота прежде всего)
Surgical Changes (точечные изменения)
Goal-Driven Execution (исполнение, ориентированное на цель)
НЕ перезаписывай существующий CLAUDE.md. Если он уже есть — добавь эти четыре принципа отдельной секцией, ничего не удаляя и не меняя. Если CLAUDE.md нет — сохрани файл как есть в корень проекта. После установки прочитай файл и подтверди, какие принципы теперь активны.

Рекомендации по поведению, позволяющие избежать распространенных ошибок при написании кода для LLM. При необходимости дополните их инструкциями, относящимися к конкретному проекту.

** Компромисс:** В этих рекомендациях предпочтение отдается осторожности, а не скорости. Для решения тривиальных задач используйте здравый смысл.

## 1. Думайте, прежде чем кодировать

** Не предполагайте. Не скрывайте замешательства. Ищите компромиссы.**

Прежде чем приступить к реализации:
- Четко сформулируйте свои предположения. Если вы не уверены, спросите.
- Если существует несколько интерпретаций, представьте их, а не выбирайте молча.
- Если существует более простой подход, скажите об этом. При необходимости дайте отпор.
- Если что-то непонятно, остановитесь. Назовите то, что вас смущает. Спросите.

## 2. Простота превыше всего

**Минимум кода, который решает проблему. Ничего умозрительного.**

- Никаких возможностей, выходящих за рамки того, что было предложено.
- Никаких абстракций для одноразового кода.
- Нет "гибкости" или "настраиваемости", которые не были запрошены.
- Нет обработки ошибок для невозможных сценариев.
- Если вы написали 200 строк, а их может быть 50, перепишите их заново.

Спросите себя: "Сказал бы старший инженер, что это слишком сложно?" Если да, то упростите.

## 3. Хирургические изменения

** Прикасайтесь только к тому, что необходимо. Убирайте только за собой.**

При редактировании существующего кода:
- Не "улучшайте" соседний код, комментарии или форматирование.
- Не проводите рефакторинг того, что не нарушено.
- Используйте существующий стиль, даже если вы бы сделали это по-другому.
- Если вы заметили несвязанный мертвый код, сообщите об этом - не удаляйте его.

Когда ваши изменения приводят к потере данных:
- Удалите импорт / переменные / функции, которые из-за ВАШИХ изменений стали неиспользуемыми.
- Не удаляйте ранее существовавший мертвый код, если вас не попросят.

Тест: Каждая измененная строка должна быть напрямую связана с запросом пользователя.

## 4. Выполнение, ориентированное на достижение цели

**Определите критерии успеха. Петли пока не проверена.**

Преобразуйте задачи в поддающиеся проверке цели:
- "Добавьте проверку" → "Напишите тесты для неверных входных данных, затем выполните их проверку"
- "Исправьте ошибку" → "Напишите тест, который ее воспроизводит, затем выполните его проверку".
- "Рефакторинг X" → "Убедитесь, что тесты прошли до и после"

Для многоступенчатых задач укажите краткий план:
```
1. [Шаг] → проверка: [проверить]
2. [Шаг] → проверка: [проверить]
3. [Шаг] → проверка: [проверить]
```

Строгие критерии успеха позволяют вам выполнять цикл независимо. Слабые критерии ("заставьте это работать") требуют постоянного уточнения.

---

** Эти рекомендации работают, если:** меньше ненужных изменений в отличиях, меньше переписываний из-за чрезмерного усложнения и уточняющих вопросов возникает до внедрения, а не после ошибок.
